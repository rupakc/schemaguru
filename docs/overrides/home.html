Out of the box

What your agent gets that names never tell it

Measured joins, refused hazards

Every candidate join is measured in both directions: match rate, coverage, fan-in. A route that pivots through a hub and multiplies rows is refused with the reason, never handed over silently.

Join graph

Values and pitfalls an agent would miss

Observed values and their counts, null rates, case drift, text-typed dates, soft-delete rules: each with its provenance and measurement date. Unknown stays unknown.

PII masked by default

Values that leave SchemaGuru follow the {{ landing.value_policy }} policy by default: anything that looks personal is replaced by its shape. {{ landing.pii_example.in | e }} becomes {{ landing.pii_example.out | e }}.

PII and value masking

Lineage from dbt and view SQL

What a table or column is built from, and what reads it, parsed from view definitions and dbt models. An agent can ask before it trusts a derived number.

Lineage

Humans override, in reviewable YAML

Descriptions, expected values, soft-delete rules, pitfalls and glossary terms live in a YAML overlay you review like code. People win; expectations are checked against the data, never rewritten.

Overlays

Works without an LLM

Crawl, measure, scope and render are plain code. A language model is optional, for drafting descriptions, and its drafts are labelled until a person accepts them.

How it works

Three steps from catalog to agent

  1. Crawl & measureRead the catalog (metadata only), then measure what the data says: which joins hold and how well, which values occur, how often a column is null.
  2. Resolve & scopeMerge measurement with your YAML overlay and optional drafts, refuse row-multiplying routes, and pick the tables a question needs within a token budget.
  3. Serve to agentsHand the view over as prompt text, the same knowledge as tools ({{ landing.tools | join(", ") }}), or through MCP and the HTTP server.
