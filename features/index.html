    Features¶

    What works out of the box in 0.2.1 (alpha). Each card links to its guide. Try it first in the playground or read the landing page for the short version.

    Crawl the catalog¶

    Reads the system catalog only, never a data row; paged, resumable, with readers for eleven warehouses. Read the guide

    Measure what joins¶

    Match rate in both directions, fan-in, observed values and null rates, each with its method and date. Read the guide

    Sample big tables¶

    Exact on small tables, a labelled representative sample on large ones; never LIMIT. Read the guide

    Join graph and refusals¶

    Path search over measured joins; a route that would multiply rows is refused, a thin join is labelled. Read the guide

    PII masking¶

    Values shown to an agent or an LLM are masked by default. Read the guide

    Overlays in YAML¶

    Humans write meaning, enums, live-rows predicates and trusted joins in reviewable files SchemaGuru never edits. Read the guide

    Lineage¶

    What a table or column is built from and what reads it, from view definitions and dbt SQL. Read the guide

    Question scoping¶

    A token-budgeted slice of the warehouse for one question, not the whole schema. Read the guide

    Rendering profiles¶

    Deterministic, fingerprinted views in the shape each kind of agent reads best. Read the guide

    Refresh and drift¶

    Incremental re-crawl and re-measure; every change is judged against the previous snapshot. Read the guide

    Runtime feedback¶

    Report a failed query and the next measurement run looks there first. Read the guide

    Agents, tools and MCP¶

    The same knowledge as prompt text, tool calls, an MCP server or framework adapters. Read the guide

    Server mode¶

    One shared knowledge store behind HTTP for several agents and replicas. Read the guide

    Drafting with an LLM (optional)¶

    An LLM drafts meanings; they are stored as drafts, marked as such, and never replace measured facts. Read the guide

    Extending¶

    Every component sits behind a small protocol: readers, stores, retrievers, providers, detectors and more. Extension points

    Readers

    The ClickHouse, DuckDB, MySQL, PostgreSQL, SQL Server and Trino readers are tested against real engines in CI. The BigQuery, Databricks, Oracle, Redshift and Snowflake readers are built from the documented system views and tested on recorded metadata, not yet validated against live accounts. Azure Synapse is supported through the SQL Server reader and is not tested in CI.

    Why it matters: a wrong guess does not error¶

    An agent that writes SQL against a warehouse knows what the names tell it. Names mislead in at least three common ways, and each returns a plausible, wrong number instead of an error. These three come from the shop warehouse SchemaGuru is tested on; the row counts are counted with plain SQL on that warehouse.

    1. The wrong join¶

    An agent asked for events per order joins orders → accounts → events on account_id. Both joins are "correct" (match rate 100%), yet the result has 3,335,000 rows for 10,000 orders — 333.5× — because both tables attribute many rows to one account. No error, a plausible number.

    SchemaGuru measured both joins, saw accounts receiving two attribution edges, and refuses the route (find_join_path / schemaguru path shop.orders shop.events):

    every route shop.orders -> shop.events pivots through hub shop.accounts on two attribution edges (fan-in > 10): a cartesian hazard

    A safe route is returned with its keys and its weakest support:

      shop.payments → shop.orders → shop.customers · support 98.04%
    payments.order_id = orders.order_id (1:1)
    orders.customer_id = customers.customer_id (N:1)

    2. The soft-delete flag that is never FALSE¶

    orders.deleted is TRUE or NULL — never FALSE. The filter an agent writes from the name, WHERE NOT deleted, returns 0 rows; the live rows are 9,700. The measured values sit next to the human's soft-delete rule:

      live rows: (deleted IS NULL OR NOT deleted) (human, unchecked)
    deleted      BOOLEAN  values: TRUE (300) (measured 2026-11-24); null 97% (measured 2026-11-24); distinct 1 (measured 2026-11-24)

    3. The enum that drifted in case¶

    WHERE status = 'paid' counts 5,000 orders; 5,412 are paid. The overlay declares paid, refunded, cancelled; measurement found PAID as well. SchemaGuru keeps the human expectation and states the contradiction (here under a waiver with an expiry date):

      ⚠ WAIVED until 2027-01-31 (legacy upper-case rows being migrated): status: declared values 'paid','refunded','cancelled' — observed also 'PAID' (412 rows)
  ⚠ status: case drift: 'paid'/'PAID' differ only in case — compare case-insensitively
    status       VARCHAR  values: 'paid','refunded','cancelled' (+ observed 'PAID'); distinct 4 (measured 2026-11-24); Payment state of the order.

    How SchemaGuru catches them¶

    Trap What SchemaGuru does Read more
    Row-multiplying join measures every candidate join in both directions (match rate, reverse coverage, fan-in); refuses a route that arrives at a hub on one many-to-one edge and leaves on another (HUB_PIVOT) Join graph
    TRUE/NULL flag measures observed values and the null rate; shows the human's live-rows predicate next to them Measure
    Case drift keeps a declared enum as an expectation, never rewrites it; reports what measurement saw beyond it Overlays
    Narrow join a thin but correct join is returned labelled with its coverage; only broken joins are refused Join graph
    Stale knowledge refresh re-measures, diffs against the previous snapshot and classifies each change Refresh

    Every statement carries its provenance (catalog, declared, measured, drafted by an LLM, or human) and every measured number carries its method and date. Unknown is shown as unknown, never as 0 or 100%. A view that shows a warning also says that the absence of a warning is not verification.

    Where it shines¶

    Agents on huge warehouses. Metadata-only, paged, resumable crawls; search runs in the store's full-text index, so a view is scoped without loading every table. Lazy, budgeted measurement: an agent's question never spends warehouse money by itself.

    Onboarding analysts. schemaguru context "<question>" prints what a newcomer needs: which tables answer it, which joins are measured, which columns hold traps.

    Data-contract CI. Declare enums, joins and soft-delete rules in YAML; schemaguru refresh exits 1 when a change needs review, and view fingerprints detect prompt drift.

    Migration audits. Measure the same joins before and after a move; the refresh report says which verdicts changed, judged relative to the previous snapshot.

    Scale¶

    Measured on the developer's machine (hardware-dependent): lexical table search over a synthetic 500,000-table store and graph expansion over 50,000 joins are fast; the whole context call at that size is not.

    At 500,000 tables the context call has a p95 of 28.6 s, which misses its 200 ms target; this is a known limit, see Scale.

    Architecture¶

    Text equivalent of the diagram
    1. The warehouse is read by catalog readers, which write to the store.
    2. Measure (through FactLang), overlays (human YAML) and lineage also write to the store; measurement queries the warehouse.
    3. The join graph and question scoping read the store.
    4. Rendering turns the scoped result into a view.
    5. Agents receive it as a prompt, tools, an MCP server, framework adapters or HTTP.
