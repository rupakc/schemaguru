    rupakc/schemaguru
    v0.2.1 · alpha · open source

    Your agent reads the names. SchemaGuru reads the data.

    Column names hide the traps that turn a plausible query into a wrong number. SchemaGuru measures what really joins and which values really occur, refuses join paths that multiply rows, and hands your agent a question-scoped view of all of it.

    Python library, CLI, MCP server and HTTP server. No LLM required.

    Out of the box

    What your agent gets that names never tell it

    Measured joins, refused hazards

    Every candidate join is measured in both directions: match rate, coverage, fan-in. A route that pivots through a hub and multiplies rows is refused with the reason, never handed over silently.

    Join graph

    Values and pitfalls an agent would miss

    Observed values and their counts, null rates, case drift, text-typed dates, soft-delete rules: each with its provenance and measurement date. Unknown stays unknown.

    Measure

    PII masked by default

    Values that leave SchemaGuru follow the masked policy by default: anything that looks personal is replaced by its shape. Ask jane.doe@example.com about order 42 becomes Ask <email> about order 42.

    PII and value masking

    Lineage from dbt and view SQL

    What a table or column is built from, and what reads it, parsed from view definitions and dbt models. An agent can ask before it trusts a derived number.

    Lineage

    Humans override, in reviewable YAML

    Descriptions, expected values, soft-delete rules, pitfalls and glossary terms live in a YAML overlay you review like code. People win; expectations are checked against the data, never rewritten.

    Overlays

    Works without an LLM

    Crawl, measure, scope and render are plain code. A language model is optional, for drafting descriptions, and its drafts are labelled until a person accepts them.

    Drafting
    How it works

    Three steps from catalog to agent

    1. Crawl & measureRead the catalog (metadata only), then measure what the data says: which joins hold and how well, which values occur, how often a column is null.
    2. Resolve & scopeMerge measurement with your YAML overlay and optional drafts, refuse row-multiplying routes, and pick the tables a question needs within a token budget.
    3. Serve to agentsHand the view over as prompt text, the same knowledge as tools (schema_context, search_tables, describe_table, find_join_path, column_values, explain_term, lineage), or through MCP and the HTTP server.

    Integrations

    Use it from¶

    One knowledge store, every surface: each calls the same Guru methods and the same tools, so an agent sees the same view wherever it runs.

    import schemaguru as sg

guru = sg.Guru.connect("duckdb:///warehouse.duckdb")  # crawls the catalog: metadata only
guru.measure(all=True)                                # what the data says: joins, values, nulls
guru.load_overlays("schemaguru.yaml")                 # what people know, in reviewable YAML
print(guru.context("monthly revenue by customer segment").text)

refused = guru.find_path("shop.orders", "shop.events")
print(refused.refusal, "-", refused.explanation)      # a route through a hub is refused
guru.close()

    This block runs as written in the docs test, on the shop warehouse. More in Getting started.

    pip install 'schemaguru[mcp,duckdb]'
schemaguru --url duckdb:///warehouse.duckdb --store .schemaguru/shop.db mcp

    Serves the tools, plus a schema://tables/{ref} resource per table, over stdio. Client configuration: Agents, tools and MCP.

    pip install 'schemaguru[duckdb]'
export SCHEMAGURU_URL=duckdb:///warehouse.duckdb
schemaguru crawl
schemaguru measure --all
schemaguru context "monthly revenue by customer segment"
schemaguru path shop.orders shop.events    # exit 1: the route pivots through a hub

    Every command: CLI reference.

    from schemaguru.agent.adapters import langchain as sg_langchain

tools = sg_langchain.tools(guru)            # StructuredTools; results are JSON text
agent_model = chat_model.bind_tools(tools)
retriever = sg_langchain.retriever(guru, k=4)   # describe_table documents per hit

    from schemaguru.agent.adapters import llamaindex as sg_llamaindex

tools = sg_llamaindex.tool_spec(guru)       # FunctionTools

    from agents import Agent

from schemaguru.agent.adapters import openai_agents as sg_openai

agent = Agent(name="analyst", instructions=guru.prompt_block(),
              tools=sg_openai.function_tools(guru))

    One extra each (langchain, llamaindex, openai-agents). See Framework adapters.

    pip install 'schemaguru[server,duckdb]'
export SCHEMAGURU_SERVER_TOKENS="$READER_TOKEN:reader"
schemaguru --url duckdb:///warehouse.duckdb --store .schemaguru/shop.db serve --port 8080

curl -s http://127.0.0.1:8080/context \
  -H "Authorization: Bearer $READER_TOKEN" -H "Content-Type: application/json" \
  -d '{"question": "monthly revenue by customer segment"}'

    The ClickHouse, DuckDB, MySQL, PostgreSQL, SQL Server and Trino readers are tested against real engines in CI. The BigQuery, Databricks, Oracle, Redshift and Snowflake readers are built from the documented system views and tested on recorded metadata, not yet validated against live accounts. Azure Synapse is supported through the SQL Server reader and is not tested in CI.

    Built to be trusted

    Nothing hidden, nothing written

    Open source, MIT

    Read the code that reads your warehouse, on GitHub.

    Read-only by design

    Metadata queries and measurement probes only. It never writes to a warehouse and never runs your agent's SQL.

    Deterministic

    No model in the loop unless you add one. Every statement carries its provenance, every measured number its method and date.

    Tested

    Every runnable example in these docs runs in CI, and every output on this page was produced by the library at build time.
